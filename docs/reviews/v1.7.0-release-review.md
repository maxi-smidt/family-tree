# Release readiness review — v1.6.0 → v1.7.0

**Scope:** every commit from tag `v1.6.0` to `HEAD` (`48b19c6`), 27 merged PRs.
**Reviewer:** senior engineer code review.
**Date:** 2026-07-10.

## Verdict

The release is **close, but not ready to tag as-is.** There is **one
high-severity data-loss regression** (documents silently deleted when a
member's birth/death date is edited) that should block the tag until fixed.
Everything else is green: both apps build and test clean locally, i18n parity
passes, the new Documents / public-tree-password / admin-audit features are
well-scoped and tree-isolated, and the Sources→Documents removal is clean (no
dead code left behind).

## Blocker

### B1 — Editing a member's birth/death date silently deletes the documents linked to that event · **High / data loss**

**Where:** `frontend/src/hooks/useMemberStore.ts:39` (caller) →
`frontend/src/hooks/useEventStore.ts:96` (`updateEvent`); the twin latent case
is `useStoryStore.ts:97` (`updateStory`).

**What changed:** this release added an *unconditional* document-link write to
`updateEvent`/`updateStory`, with the argument defaulting to `[]`:

```ts
// useEventStore.ts
updateEvent: async (id, event, memberIds, documentIds: string[] = []) => {
  await TreeService.updateEvent(treeId, id, event);
  await TreeService.setEventLinks(treeId, id, memberIds);
  await TreeService.setEventDocuments(treeId, id, documentIds); // ← replaces ALL links; [] wipes them
  ...
}
```

`setEventDocuments` is a **replace-the-whole-set** endpoint
(`PUT /events/{id}/documents`). Calling it with `[]` removes every document
link on the event.

**How it fires:** whenever a member's `dateOfBirth` / `dateOfDeath` changes,
`updateMemberPartial` calls `syncVitalEvent`, which updates the matching
birth/death event **without** passing document ids:

```ts
// useMemberStore.ts:39 — inside syncVitalEvent()
await updateEvent(existing.id, { eventType, date: newDate }, [memberId]);
//                                                            ^ no documentIds → defaults to []
```

Because the member edit sheet now **autosaves** (v1.7.0, PR #618), this path is
hit routinely, not just on an explicit save.

**Reproduction:**
1. Open a member, attach a document (e.g. a birth certificate) to their **birth**
   event via the timeline/event dialog.
2. Change that member's birth date in the member sheet (autosave fires).
3. `syncVitalEvent` → `updateEvent(..., [memberId])` → `setEventDocuments(id, [])`.
4. The birth-certificate link is gone, silently. No toast, no confirmation.

**Why tests miss it:** `useMemberStore.test.ts` mocks `TreeService.getEvents`
to `[]`, so `syncVitalEvent`'s `existing` event is never found and the
destructive branch is never exercised.

**Fix options (pick one):**
- Preferred: make the document write opt-in. Change the signature to
  `documentIds?: string[]` (no `= []` default) and guard the call —
  `if (documentIds !== undefined) await TreeService.setEventDocuments(...)`.
  This matches how `addEvent` already guards (`if (documentIds.length > 0)`)
  and means "not supplied" ≠ "clear all". Apply the same to `updateStory`.
- Or: in `syncVitalEvent`, thread the existing links through —
  `updateEvent(existing.id, { eventType, date: newDate }, existing.linkedMemberIds, existing.documentIds)`.
  (`Event` now carries both `linkedMemberIds` and `documentIds` in the store,
  so they're available.) Note this also fixes a pre-existing secondary quirk:
  `syncVitalEvent` currently resets the event's member links to just
  `[memberId]`, dropping any extra people linked to that vital event.
- Add a regression test with a non-empty `getEvents` mock that asserts
  `setEventDocuments` is **not** called (or called with the preserved set)
  when a DOB/DOD edit triggers `syncVitalEvent`.

## Should-fix before release

### S1 — Upgrading to v1.7.0 permanently drops all Sources / Citations / Story-attachment data, and this isn't clearly communicated · **Medium**

**Where:** `backend/alembic/versions/v1_7_0_documents.py:89-105`.

The migration drops `story_attachments`, `citations`, `source_evidence`, and
`sources` outright — the code comment is explicit: *"data is dropped outright —
it is not migrated into the new Documents model."* That is a legitimate product
decision, but two consequences are under-handled:

1. **User communication.** The `CHANGELOG.md` `[Unreleased]` entry describes the
   *rename/rework* but never warns self-hosters that **existing source
   citations and story attachments are destroyed** on `alembic upgrade head`
   (which runs automatically on backend startup). For a self-hosted genealogy
   app this is exactly the kind of irreversible loss that deserves a loud
   **Security/Changed** note and an upgrade caveat in the release notes.
2. **Orphaned media on disk.** The dropped `story_attachments` and file-kind
   `source_evidence` rows pointed at real files under
   `DATA_PATH/media/<tree_id>/`. The migration removes the DB rows but nothing
   deletes those bytes, so they leak on disk permanently (they also no longer
   count against storage quota, so usage numbers and reality diverge). Consider
   a one-shot cleanup, or at least document the leak.

### S2 — Importing a pre-v1.7.0 backup silently discards its sources/citations/attachments · **Medium**

**Where:** `backend/app/api/routes/export_import.py:65,84-104`.

`BUNDLE_VERSION` is still `2` (unchanged from v1.6.0), but the bundle schema
changed materially: v1.6.0 bundles carry `sources` / `source_evidence` /
`citations` / `story_attachments`; v1.7.0 reads `documents` /
`document_files` / `*_document_links`. Because the version number didn't move,
a v1.6.0 `.treedb` imports **without any "newer/older version" signal**, and
`migrate_bundle()` is a no-op — so the old keys are silently ignored and that
data is dropped on import.

Recommend bumping `BUNDLE_VERSION` to `3` and adding a `migrate_bundle` step
that best-effort maps old `sources`+`source_evidence` into `documents`+
`document_files` (and `citations`/`story_attachments` into member/story
document links). At minimum, detect the old keys and surface a warning so the
loss is not silent.

## Nice-to-have / hardening (non-blocking)

### N1 — External document links accept any URL scheme (stored-XSS surface) · Low, pre-existing
`backend/app/api/routes/documents.py:374-378` rejects only `data:` and
`/api/media/` link URLs; `javascript:` / `vbscript:` pass. The link is later
rendered as `<a href={f.url}>` in
`frontend/src/components/shared/member-sheet/DocumentFiles.tsx:96-106`. An
editor could plant a `javascript:` link that runs when a viewer (or a public
visitor) clicks it. This behaviour is **carried over unchanged** from the old
Sources evidence code, so it's not a v1.7.0 regression — but Documents surface
far more widely (every mentioned person's profile, plus events and stories,
visible to viewers and public trees), so the exposure is larger now. Recommend
allowlisting `http:`/`https:` (and maybe `mailto:`) server-side.

### N2 — `updateDocument` doesn't roll back partial file-op failures · Low
`frontend/src/hooks/useDocumentStore.ts:139-161`: `addDocument` carefully rolls
the new document back if any attachment upload fails, but `updateDocument`
applies delete→rename→add sequentially *after* committing the metadata/member
changes, with no rollback. A mid-sequence failure (e.g. a 413 on one added
file) leaves the document partially updated and throws. Consider refreshing and
messaging consistently, mirroring the add path.

### N3 — `serve_media` now runs a DB query on every media request · Low (perf)
`backend/app/api/routes/media.py` looks up a `DocumentFile` by `url` on **every**
media fetch to recover the original download filename — including member photos
and gallery thumbnails, which never have a `DocumentFile` row. `document_files.url`
is an unindexed `Text` column (only `tree_id`/`document_id` are indexed), so this
adds an extra query to the hot image-serving path. Fine at small scale; if it
shows up, gate the lookup (e.g. only when a `download` query param is present) or
index the lookup.

### N4 — Minor changelog/style nits · Trivial
- `CHANGELOG.md` `[Unreleased]` has two near-duplicate "#634" frozen-header
  Fixed entries — collapse into one.
- `export_import.py` re-imports `sqlalchemy.inspect` inside `_rows` and
  `_document_link_rows` (function-local import); pre-existing pattern, harmless.
- `backend/app/api/routes/virtual_views.py:629,633` use `.fetchall().__len__()`
  where `len(...)` reads more idiomatically.

## What was reviewed and looks good

- **Tree isolation.** Every new Documents query is scoped by `tree_id`
  (`documents.py`, `content_links.py`, `storage_usage.py`), and the document
  link tables (no `tree_id` of their own) are consistently joined through
  `Document` for scoping in export, storage-usage, extract, and merge.
- **Public-tree password.** Hashing via bcrypt, a dummy-verify on the
  unlock endpoint to avoid a timing oracle
  (`trees.py:unlock_public_tree`), a short-lived (`12h`) phase-scoped JWT
  (`core/security.py`), in-memory-only token on the client
  (`services/api.ts`), and the hash is never serialized (only a
  `public_password_protected` boolean is exposed). Clearing `public_role`
  also clears the hash. Solid.
- **Admin audit trail.** Independent of trees (survives tree deletion, unlike
  the per-tree activity log), no write API, indexed on `actor_id` /
  `subject_type` / `created_at`, and `record_admin_audit` explicitly documents
  "never put credentials in `details`" — call sites honour it (password changes
  log only a boolean). Routes that previously took no actor now require
  `require_admin` and capture the actor.
- **Extract / merge / GEDCOM / export-import.** Document copy-and-repoint on
  subtree extract, orphan GC in the source tree, file-byte accounting in the
  preview, and the SOUR/OBJE GEDCOM mapping are all handled and covered by the
  new tests (`test_extract_move`, `test_merge`, `test_content`,
  `test_public_access`, `test_admin_audit`).
- **Clean removal.** `useSourceStore`, `types/source`, `MemberSources`,
  `SourceCitationDialog`, `StoryAttachments`, and `routes/sources.py` are fully
  deleted; the only remaining "source" mentions are intentional explanatory
  comments. `models/__init__` and `api/router` are updated consistently.
- **nginx upload ceiling** raised from 50m → 700m with a clear rationale
  comment tying it to `MAX_MAX_DOCUMENT_UPLOAD_MB`; fixes the real #593 bug
  where the proxy capped uploads below the configurable backend limit.
